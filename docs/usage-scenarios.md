## 1. Карта возможностей

| Возможность | Что даёт | Когда включать | Где подробно |
|---|---|---|---|
| Профили (`oc`, `oc-dev`, …) | изолированные наборы MCP, агентов, прав и модели | выбрана роль на задачу | [profiles-agents-matrix.md](profiles-agents-matrix.md) |
| Проектный `opencode.jsonc` | добавляет MCP и агентов проекта к базовому профилю | проекту нужны две и более роли | [multi-profile-projects.md](multi-profile-projects.md) |
| Кастомные агенты | персона с узкой специализацией | архитектура, ревью, аудит, инцидент | [custom-agents.md](custom-agents.md) |
| Скиллы | готовые процедуры (TDD, ревью, rollout, Vault) | повторяемая задача | [skills-selection.md](skills-selection.md) |
| MCP | доступ к Docker, БД, Proxmox, GitLab, браузеру | нужны внешние системы | [profiles-agents-matrix.md](profiles-agents-matrix.md) |
| `/mcp off|only|reset` | скрыть лишние серверы в текущей сессии | контекст перегружен | [mcp-sets.md](mcp-sets.md) |
| Контекст-леджер | `INDEX.md` → `current.md` → `decisions.md` | любая задача длиннее одного шага | [context-management.md](context-management.md) |
| DCP, `/compact`, `compress` | экономия контекста и токенов | сессия разрослась | [context-management.md](context-management.md) |
| SuperMemory | память между сессиями | возврат к теме через дни | [methodology.md](methodology.md) |
| Handoff | новая сессия с готовым промптом и файлами | контекст пора разделить | плагин `opencode-handoff` |
| Vault (`agent-vault`) | секреты вне конфигов и истории | пароли, токены, ключи | скилл `agent-vault` |
| `opencode_sync` | перенос конфига между машинами | новая машина, бэкап | [../README.md](../README.md) |
| Публичный шаблон | обезличенная копия конфигурации | передача людям | [../scripts/public-export/README.md](../scripts/public-export/README.md) |
| Тесты конфигурации | защита от дрейфа | перед коммитом | [../AGENTS.md](../AGENTS.md) |

**Главное правило:** конфигурацию правят в репозитории (`config/`,
`profiles/`), а не в `~/.config/opencode*`. Runtime-каталоги — результат
`setup.sh` и `opencode_sync pull`; ручные правки там теряются при следующей
синхронизации.

## 2. Три уровня конфигурации

OpenCode складывает настройки от общего к частному:

```text
~/.config/opencode/opencode.json              глобальный default
        ↓
~/.config/opencode-<profile>/opencode.json    выбранный профиль (ocp)
        ↓
<project>/opencode.json | opencode.jsonc      проектный слой
```

Правила слияния:

- `mcp.servers` и `agent` **объединяются**;
- при совпадении имени побеждает более поздний слой;
- `model`, `permissions`, `instructions`, плагины берутся из базового профиля;
- проектный конфиг действует только в каталоге проекта и ниже;
- после правки проектного файла — `opencode reload` (или перезапуск `ocp`).

Проверка, что реально загрузилось:

```bash
opencode debug config      # итоговый конфиг и источники
opencode debug agents      # агенты профиля + проекта
opencode mcp list          # MCP профиля + проекта
```

## 3. Первый запуск на новой машине

### 3.1. Установка

```bash
# приватный репозиторий: нужен авторизованный gh
gh auth status

gh repo clone YOUR_ORG/my-opencode-config
cd my-opencode-config
bash setup.sh --dry-run     # посмотреть план
bash setup.sh               # разложить конфиги и алиасы
source ~/.zshrc             # или ~/.bashrc
```

Если конфиг уже синхронизирован через opencode-synced:

```bash
opencode_sync pull
```

### 3.2. Секреты

```bash
agent-vault status central
agent-vault login central     # если хранилище заблокировано
```

Значения не печатать в чат и не записывать в файлы. Проверка наличия секрета
без вывода значения:

```bash
agent-vault use 'имя секрета' --project YOUR_PROJECT -- 'test -n "$VAULT_PASSWORD" && echo ok'
```

### 3.3. Проверка

```bash
oc --version
opencode debug config | jq -r '.model'
opencode mcp list
ocp dev                       # запуск в профиле dev
```

В репозитории конфигурации:

```bash
python3 tests/validate_configs.py config profiles
python3 -m pytest tests -q
```

Ожидаемо: схема без ошибок, тесты зелёные, MCP-серверы выбранного профиля
видны, `default` — без MCP.

## 4. Новый проект с нуля

### 4.1. Выберите базовый профиль

Профиль задаёт модель, права и основной набор инструментов. Не выбирайте
«на всякий случай» самый тяжёлый: лишние MCP-серверы расходуют контекст.

| Что за проект | Профиль |
|---|---|
| код, БД, Docker, GitHub | `dev` |
| инфраструктура, IaC, K8s | `infra` |
| сеть, firewall, VPN | `net` |
| безопасность, пентест | `sec` |
| АСУ ТП / ICS | `ot` |
| PRD, аналитика, инциденты | `mgnt` |
| UI/UX, вёрстка, визуальная приёмка | `design` |

### 4.2. Создайте проект и `AGENTS.md`

```bash
mkdir -p ~/projects/my-service
cd ~/projects/my-service
git init
```

`AGENTS.md` в корне проекта — главный способ передать агенту правила проекта.
Минимальный шаблон:

```markdown
# my-service

## Стек
Python 3.12, FastAPI, PostgreSQL, Docker Compose.

## Команды
- установка: `make install`
- тесты: `make test`
- линт: `make lint`
- запуск: `docker compose up -d`

## Правила
- не менять схему БД без миграции;
- секреты — только через Vault, не в `.env`;
- публичные функции — с типами и тестами.

## Готово, когда
- `make test` и `make lint` зелёные;
- обновлён `README.md`, если изменился интерфейс.
```

OpenCode читает `AGENTS.md` из проекта автоматически. Если у проекта уже есть
`README.md` и `CONTRIBUTING.md`, не дублируйте их — ссылайтесь на них.

### 4.3. Запустите сессию

```bash
ocp dev
```

Дальше — по методологии:

1. `writing-plans` — план для сложной задачи;
2. `test-driven-development` — тесты до реализации;
3. `@code-architect` — границы модулей и интерфейсы;
4. `@senior-python-dev` (или другой язык) — реализация;
5. `@code-reviewer` — ревью перед коммитом;
6. `verification-before-completion` — проверка перед заявлением «готово».

Пример первого сообщения:

```text
Создай скелет сервиса по AGENTS.md. Сначала предложи план и структуру,
затем реализуй по TDD. Ничего не коммить без моего подтверждения.
```

### 4.4. Заведите контекст-леджер

Для задачи длиннее одного шага:

```bash
# глобальный леджер конфигурации
cat ~/.config/opencode/context/INDEX.md
cat ~/.config/opencode/context/current.md
```

В `current.md` зафиксируйте objective, ограничения, решения, файлы и следующий
шаг. После каждой вехи обновляйте его. Завершённую задачу переносите в
`context/archive/` и добавляйте строку в `INDEX.md`.

### 4.5. Когда нужен проектный конфиг

Если проекту достаточно одного профиля — проектный файл не нужен. Если нужны
роли из двух профилей (код + инфраструктура), см. [раздел 8](#8-проект-на-нескольких-профилях).

### Чек-лист нового проекта

- [ ] выбран базовый профиль;
- [ ] создан `AGENTS.md` с командами и критериями готовности;
- [ ] `make test` / аналог проходит до первого изменения;
- [ ] заведён `current.md` (или запись в существующем леджере);
- [ ] секреты не попали в репозиторий;
- [ ] `.gitignore` закрывает `.env`, БД, артефакты.

## 5. Уже начатый проект: подключить существующий код

Ситуация: код уже есть, OpenCode раньше не использовался.

### 5.1. Сначала — разведка, без изменений

```bash
cd ~/projects/legacy-service
git status
rg --files -g 'README*' -g 'AGENTS.md' -g 'Makefile' -g 'docker-compose*' -g '*.tf'
```

Запустите сессию и попросите только прочитать проект:

```bash
ocp dev
```

```text
Изучи проект, ничего не меняй. Составь карту модулей, команд сборки и тестов,
внешних зависимостей и рисков. Предложи, что записать в AGENTS.md.
```

Полезные агенты на этом шаге: `@code-architect` (структура),
`@appsec-auditor` (риски), `@code-reviewer` (качество).

### 5.2. Зафиксируйте базовую линию

До любых правок:

```bash
make test        # или pytest / npm test / go test ./...
make lint
```

Результат запишите в `AGENTS.md` или в `current.md`: что уже сломано, что
проходит. Иначе агент примет существующие ошибки за свои.

### 5.3. Создайте `AGENTS.md` из того, что уже есть

Не переписывайте документацию — соберите правила:

```markdown
# legacy-service

## Стек
PHP 8.2, Symfony, MySQL 8, Docker Compose.

## Команды
- тесты: `composer test`
- линт: `composer lint`
- миграции: `bin/console doctrine:migrations:migrate`

## Ограничения
- не менять публичные API без версии;
- не трогать `legacy/` без отдельной задачи;
- секреты — только Vault.

## Известные проблемы
- `composer test` падает на 3 тестах интеграции с БД (см. issue #42).
```

### 5.4. Добавьте проектный конфиг, если ролей несколько

```bash
oc-project-init.py --profiles dev,infra
opencode reload
```

Скрипт соберёт `opencode.jsonc` с MCP и агентами обоих профилей. Модель и права
останутся от базового профиля (`ocp dev`). Подробности —
[multi-profile-projects.md](multi-profile-projects.md).

### 5.5. Первая задача — маленькая

Не начинайте с рефакторинга. Возьмите один тест, один баг или одну функцию:

```text
Исправь падающий тест X. Сначала воспроизведи, затем предложи минимальную
правку, добавь регрессионный тест, прогони весь набор.
```

Так вы проверите, что агент понимает проект, а `AGENTS.md` — достаточен.

### Чек-лист подключения существующего проекта

- [ ] проект прочитан без изменений;
- [ ] зафиксирована базовая линия тестов и линта;
- [ ] создан `AGENTS.md` (стек, команды, ограничения, известные проблемы);
- [ ] при необходимости сгенерирован `opencode.jsonc`;
- [ ] секреты вынесены в Vault, `.env` в `.gitignore`;
- [ ] первая задача — небольшая и проверяемая;
- [ ] `opencode debug config` показывает ожидаемые слои.

## 6. Проект, начатый в другом агенте или IDE

Ситуация: проект уже ведётся в Cursor, Claude Code, Copilot или другом
инструменте; там есть свои правила и команды.

### 6.1. Перенесите правила в `AGENTS.md`

| Откуда | Что перенести |
|---|---|
| `CLAUDE.md` | правила, команды, ограничения — в `AGENTS.md` |
| `.cursor/rules/*` | постоянные правила — в `AGENTS.md`; разовые процедуры — в скилл |
| `.github/copilot-instructions.md` | то же |
| `CONTRIBUTING.md` | не копировать, дать ссылку |

`AGENTS.md` — обычный Markdown. Держите его коротким: он попадает в контекст
каждого запроса. Длинные процедуры выносите в скиллы или в `docs/`.

### 6.2. Не дублируйте команды

Если в старом инструменте были слэш-команды, у нас есть два пути:

- повторяемая процедура для всех проектов → скилл в `config/skills/`
  (см. [skill-management.md](skill-management.md));
- правило конкретного проекта → раздел в `AGENTS.md`.

### 6.3. Сопоставьте инструменты

| Было | Стало |
|---|---|
| встроенный чат по файлам | `read`/`grep`/`edit` + `@code-reviewer` |
| терминал | `bash` с подтверждением (`permissions`) |
| браузер | MCP `playwright` (dev/mgnt/ot) |
| БД | MCP `postgres` (dev/infra/mgnt) |
| GitHub/GitLab | MCP `github` / `gitlab-*` (dev, infra) |
| секреты в настройках IDE | Vault через `agent-vault` |

### 6.4. Что не переносится

- история чатов и сессий другого инструмента;
- его кэш и индексы;
- токены и пароли из его настроек — заново положите в Vault.

После переноса проверьте: `opencode debug config`, `opencode mcp list`, первый
запрос «прочитай проект и перескажи правила».

## 7. Перенос проекта на другую машину

### 7.1. Что переносится

| Переносится | Не переносится |
|---|---|
| код и `AGENTS.md` | история сессий (`includeSessions: false`) |
| `opencode.jsonc` проекта | SuperMemory и локальные кэши |
| конфигурация через git | секреты Vault (нужен доступ к Vault) |
| `docs/`, планы, решения | значения `.env` и локальные пути |

### 7.2. Порядок

На новой машине:

```bash
# 1. конфигурация
gh repo clone YOUR_ORG/my-opencode-config
cd my-opencode-config && bash setup.sh
source ~/.zshrc

# 2. синхронизация runtime-конфига
opencode_sync pull

# 3. секреты
agent-vault login central

# 4. проект
gh repo clone YOUR_ORG/my-service ~/projects/my-service
cd ~/projects/my-service

# 5. проверка проектного конфига
oc-project-init.py --profiles dev,infra --check   # если файл есть
ocp dev
```

Если `--check` вернул ошибку — проектный конфиг отстал от профилей:

```bash
oc-project-init.py --profiles dev,infra
opencode reload
```

### 7.3. Продолжение работы

Сессии не переезжают. Восстановите контекст из артефактов:

- `AGENTS.md` и `README.md`;
- `context/current.md` (если переносили леджер);
- последние коммиты и PR;
- `docs/` и планы.

Первый запрос: «прочитай AGENTS.md и последние коммиты, восстанови состояние,
предложи следующий шаг».

## 8. Проект на нескольких профилях

Ситуация: нужен код и инфраструктура, или разработка и визуальная приёмка.

```bash
cd ~/projects/my-service
oc-project-init.py --profiles dev,infra
ocp dev
```

Что произойдёт:

- `dev` задаёт модель, права и `default_agent`;
- в `opencode.jsonc` добавятся MCP и агенты `infra`;
- при совпадении имён побеждает профиль, указанный позже;
- скрипт печатает конфликты.

Проверка и обновление:

```bash
opencode mcp list
opencode debug agents

oc-project-init.py --profiles dev,infra --check
oc-project-init.py --profiles dev,infra          # перегенерировать
```

`--check` удобно добавить в pre-commit или CI проекта: тогда дрейф между
профилями и проектом не накопится.

Альтернативы:

- **фазы**: `ocp dev` → работа → `ocp infra -s <session-id>` (история та же,
  инструменты другие);
- **`/mcp only`**: оставить в сессии только нужные серверы, не добавляя новых.

Подробно — [multi-profile-projects.md](multi-profile-projects.md).

## 9. Возобновление прерванной работы

### 9.1. Вернуться в ту же сессию

```bash
ocp dev                 # продолжит последнюю сессию проекта (--continue)
ocp dev -s <session-id> # конкретная сессия
```

Новая сессия — `leader+n` в TUI; так же начинается «чистый лист».

### 9.2. Восстановить состояние из леджера

```text
Прочитай context/INDEX.md и context/current.md, затем только те файлы,
на которые они ссылаются. Кратко восстанови состояние и продолжи с next step.
```

Если леджера нет — попросите агента собрать его из `git log`, `README.md` и
`docs/`, прежде чем продолжать.

### 9.3. Если контекст разросся

- `/compact` — ручная компакция истории;
- `/dcp` — состояние DCP и потребление контекста;
- `/dcp-compress` — принудительное сжатие;
- скилл `compress` — сжать файл памяти, сохранив техническую суть;
- `caveman` — сверхсжатый режим общения, когда важна экономия токенов.

### 9.4. Передать работу в новую сессию

Плагин `opencode-handoff` создаёт новую сессию с промптом и файлами. Попросите:

```text
Сделай handoff в новую сессию. В промпт включи: цель, текущее состояние,
принятые решения, следующий шаг и ограничения. Приложи context/INDEX.md,
context/current.md, context/decisions.md и 2–3 ключевых файла.
```

Handoff полезен, когда:

- контекст переполнен, а задача ещё не закрыта;
- нужно разделить исследование и реализацию;
- работу продолжит другой профиль или другая машина.

### 9.5. Вспомнить прошлые решения

SuperMemory хранит решения между сессиями. На старте задачи:

```text
Вспомни, что мы решали по <теме>, и не повторяй отклонённые варианты.
```

Recall идёт по теме текущей задачи, а не по всему хранилищу.

## 10. Секреты и чувствительные проекты

### 10.1. Правила

- секреты — только в Vault (`secret/agent/<project>/<name>`) или `{env:...}`;
- не печатать значения в чат, не писать в файлы, не коммитить;
- в проектном `opencode.jsonc` и `AGENTS.md` — только имена переменных;
- `.env` — в `.gitignore`, рядом держите `.env.example`.

### 10.2. Типовой цикл

```bash
# сохранить
agent-vault set 'db password' --project my-service

# проверить наличие, не выводя значение
agent-vault use 'db password' --project my-service -- 'test -n "$VAULT_PASSWORD" && echo ok'

# выполнить команду с секретом в окружении
agent-vault use 'db password' --project my-service -- 'psql "$DATABASE_URL" -c "select 1"'
```

### 10.3. Чувствительный проект

- выберите `sec` для аудита и пентеста, `dev` — для повседневной разработки;
- перед изменениями infra — dry-run / `--check`;
- для сети — read-only first, изменения после backup;
- для АСУ ТП — активные действия только через `scripts/ot-guard.sh`;
- перед коммитом — `security-secrets` и `security-audit`.

Пример:

```bash
ocp sec
```

```text
Проведи аудит этого репозитория по OWASP Top 10. Ничего не меняй.
Секреты не выводи — только пути и рекомендации.
```

## 11. Передача конфигурации другим людям

### 11.1. Публичный шаблон

```bash
gh repo clone YOUR_ORG/opencode-config-template

```

В шаблоне заменены личные данные на плейсхолдеры: `YOUR_ORG`, `YOURUSER`,
`YOURHOST`, `YOUR_PROJECT`, примерами доменов и IP. Перед использованием
замените их на свои.

Публичная версия собирается из рабочей вручную:

```bash
scripts/export-public.sh            # обновить локальную копию и закоммитить
scripts/export-public.sh --push     # + push
```

Правила вычистки и публичный оверлей — `scripts/public-export/`.

### 11.2. Передача проекта

Передавайте:

- код и `AGENTS.md`;
- `opencode.jsonc`, если он есть;
- `README.md`, `docs/`, инструкции по запуску;
- `.env.example`.

Не передавайте:

- `.env`, токены, ключи, cookies;
- историю сессий и кэши;
- доступы к Vault — только через отдельный секрет.

### 11.3. Онбординг получателя

1. установить конфигурацию (`setup.sh`);
2. получить доступ к Vault или завести свои секреты;
3. клонировать проект;
4. `ocp <profile>`;
5. первый запрос: «прочитай `AGENTS.md`, проверь окружение, предложи план».

- `caveman-commit` — короткое сообщение коммита;
- `find-skills` — найти и установить новый скилл.

## 14. Анти-паттерны

- **Копировать профиль «dev+infra» целиком.** Он разъедется с исходными.
  Используйте проектный overlay.
- **Писать секреты в `opencode.jsonc` или `AGENTS.md`.** Только Vault или
  `{env:...}`.
- **Править `~/.config/opencode*` вручную.** Следующий `opencode_sync pull`
  перезапишет; правьте репозиторий.
- **Переключать профиль посреди задачи**, если следующий шаг зависит от MCP
  предыдущего. Сначала соберите проектный конфиг.
- **Начинать с большого рефакторинга** в незнакомом проекте. Сначала разведка,
  базовая линия и маленькая задача.
- **Считать, что сессии синхронизируются.** Они локальные
  (`includeSessions: false`); передавайте состояние через леджер и handoff.
- **Забывать `opencode reload`** после правки проектного конфига.
- **Держать `AGENTS.md` на 500 строк.** Он в контексте каждого запроса;
  длинное — в `docs/` или скиллы.
