# Один проект — несколько профилей

Профиль — это не набор галочек, а отдельный конфиг и отдельный сервер OpenCode
(`ocp <profile>` → `OPENCODE_CONFIG=~/.config/opencode-<profile>/opencode.json`,
`opencode --standalone`). Два профиля одновременно включить нельзя, но можно
собрать нужный набор инструментов под проект.

## Как OpenCode складывает конфиги

Проверено на OpenCode v2.3.0 (`opencode debug config`):

1. глобальный default — `~/.config/opencode/opencode.json`;
2. профиль — `OPENCODE_CONFIG=~/.config/opencode-<profile>/opencode.json`;
3. проектный конфиг — `<project>/opencode.json` или `<project>/opencode.jsonc`.

Правила слияния:

- `mcp.servers` и `agent` **объединяются**;
- при совпадении имени побеждает более поздний слой (проект перекрывает профиль);
- `model`, `permissions`, `instructions`, плагины берутся из базового профиля;
- после правки проектного конфига нужен `opencode reload` (или перезапуск
  `--standalone`), иначе работает старый кэш.

## Три схемы

| Схема | Когда | Плюсы | Минусы |
|---|---|---|---|
| **Базовый профиль + проектный конфиг** | роли нужны постоянно (код + инфраструктура) | одна сессия, один контекст, набор версионируется вместе с проектом | конфиг надо поддерживать |
| **Переключение по фазам** | роли разнесены во времени (сначала код, потом деплой) | ничего не дублируется | контекст и инструменты меняются вместе с профилем |
| **Один профиль + `/mcp`** | инструментов слишком много, но добавлять нечего | быстро, без файлов | не добавляет отсутствующие серверы |

Рекомендация по умолчанию — первая схема.

## Схема 1: базовый профиль + проектный конфиг

Выберите профиль, который задаёт модель, permissions и основных агентов
(обычно доминирующая роль), а недостающие MCP-серверы и агентов добавьте в
проект.

```bash
cd ~/projects/my-service
oc-project-init.py --profiles dev,infra
ocp dev
```

Скрипт создаёт `opencode.jsonc`:

```jsonc
{
  // Generated by oc-project-init.py from: dev, infra
  // Model, permissions and tools come from the base profile (ocp <profile>).
  "$schema": "https://opencode.ai/config.json",
  "mcp": { "servers": { /* объединение dev + infra */ } },
  "agent": { /* объединение агентов */ }
}
```

Что важно:

- базовый профиль (`dev`) даёт модель и права, проектный файл — только MCP и агентов;
- одинаковые имена серверов перекрываются: побеждает профиль, указанный позже
  (`--profiles dev,infra` → `infra` перекрывает `dev`), скрипт печатает конфликты;
- секреты — только `{env:...}` или Vault, в проектном файле их быть не должно;
- файл коммитится в репозиторий проекта: у всех участников одинаковый набор.

Проверка:

```bash
opencode mcp list          # профиль + проектные серверы
opencode debug agents      # профиль + проектные агенты
opencode debug config      # откуда взят каждый слой
```

Обновление после изменения профилей:

```bash
oc-project-init.py --profiles dev,infra --check   # exit 1, если отстал
oc-project-init.py --profiles dev,infra           # перегенерировать
```

`--check` удобно ставить в pre-commit или CI проекта.

### Пример: сервис + деплой

Задача: писать код и тут же готовить инфраструктуру.

```bash
cd ~/projects/my-service
oc-project-init.py --profiles dev,infra
ocp dev
```

В проект попадут `proxmox`, `ansible`, `opentofu` и агенты infra, но модель,
права и `default_agent` останутся от `dev`. Если infra-агенты не нужны:

```bash
oc-project-init.py --profiles dev,infra --no-agents
```

## Схема 2: переключение по фазам

Подходит, когда роли не пересекаются: реализация → деплой → аудит.

```bash
ocp dev
# ... работа, сессия запомнена
ocp infra -s <session-id>     # продолжить ту же сессию в infra
```

`-s/--session` и `--continue` сохраняют историю, но набор инструментов и
permissions берутся из текущего профиля. Не переключайтесь посреди задачи, если
следующий шаг зависит от MCP предыдущего профиля.

## Схема 3: один профиль и `/mcp`

Плагин `opencode-mcp-sets` скрывает серверы в текущей сессии:

```text
/mcp only docker,postgres
/mcp off gitlab-official-*
/mcp reset
```

Это уменьшает шум и число инструментов в контексте, но не добавляет серверы,
которых нет в профиле. Для добавления — схема 1.

## Автоматизация

`scripts/oc-project-init.py`:

| Опция | Назначение |
|---|---|
| `--profiles dev,infra` | какие профили объединить (обязательно) |
| `--dir DIR` | каталог проекта (по умолчанию текущий) |
| `--no-agents` | только MCP-серверы |
| `--dry-run` | показать результат, ничего не писать |
| `--check` | exit 1, если проектный файл отстал от профилей |
| `--force` | перезаписать файл, созданный не этим инструментом |
| `--config-home DIR` | альтернативный `~/.config` (для тестов) |

Источники: установленные конфиги `~/.config/opencode-<profile>/opencode.json`,
fallback — `profiles/<profile>/opencode.jsonc` из этого репозитория.

## Ограничения и подводные камни

- **Не создавайте глобальный профиль «dev+infra»** копированием конфигов: он
  разъедется с исходными. Проектный overlay — единственная точка правки.
- Проектный конфиг не меняет модель и permissions — это делает базовый профиль.
- Одноимённый MCP-сервер перекрывается целиком, а не по полям.
- `disabled: true` переносится как есть.
- Конфиг действует только в каталоге проекта и ниже.
- После правки — `opencode reload`; при `--standalone` достаточно перезапуска.
- Vault-токены не попадают в проектный файл: только `{env:...}`.
